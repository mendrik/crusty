# Crusty 0.3 state, retrieval, and migration

Crusty separates live navigation, rebuildable repository intelligence, and durable human/project memory. This separation is the core authority boundary: current source and runtime/compiler behavior remain authoritative, indexed relationships are freshness-labelled guidance, and autonomous findings remain proposals until a human acts on them.

## Authority and freshness

`repo.search(mode=exact)` reads Rust source from the live worktree and never refreshes the index. It is the preferred path for identifiers, call sites, and compiler-error navigation.

`repo.search(mode=broad)` and `repo.context` read the last atomically published index generation. Their responses include a freshness envelope containing the live and indexed revisions, generation, staleness with a `reason` (`ok`, `never_published`, `indexer_outdated`, `head_moved`, `worktree_changed`, `refresh_running`, or `error`), the running or last completed refresh, and confidence. Reads never wait for a refresh. Staleness compares live index inputs with the published input state: only inputs that are dirty now or were dirty when indexed are re-hashed, so a refreshed dirty tree is fresh and non-inputs such as Crusty's state directory or `target/` never make it stale.

`repo.architecture` reads current manifests and Rust syntax directly from the live worktree. Its versioned facts and contextual findings are labelled separately from the published relationship graph. `audit.start` runs the same bounded analysis as a durable background task and persists its completed report.

`index.status` reports the resolved workspace root, the snapshot boundary in a single index block, the latest refresh task's compact result (generation, counts, timing, and recomputed versus reused vectors), the background refresher, and the publisher lock. `index.refresh` is the explicit refresh entry point; unless `CRUSTY_AUTO_REFRESH=0`, the server's background refresher also runs the incremental refresh as a durable task after debounced file changes and `HEAD` moves, and once shortly after startup when the index is stale. It returns a task ID immediately; `task.list` recovers bounded task summaries after an interrupted session and `task.get` exposes one task's queued, running, completed, or failed state and full result. Readers keep using the previous generation while a single writer builds and publishes the replacement.

Indexed source ranges are read from the live worktree and hash-checked against indexed content. A same-length edit is still stale; returned hashes describe the current range, and missing live source has no current hash. Stale ranges have reduced confidence and explicit provenance.

The MCP server owns one persistent rust-analyzer companion, off until `semantic.enable` (or the autostart switch). When enabled, it is warmed in the background (or started by the first semantic use when warm start is disabled); refresh never starts it. Source edits are synchronised into the running companion; only analyzer-profile changes (version, options, toolchain, Cargo configuration) restart it. Cached semantic evidence is reused only when source and semantic-profile identities still match.

`index.refresh` defaults to `scope="incremental"`. Only a store that was never indexed or was written by another indexer version is rebuilt in full; `scope="workspace"` (alias `full`) forces a full rebuild. An incremental refresh re-parses changed Rust files while keeping node ids for symbols that still exist, re-derives syntax edges only for those files and for files whose references they can affect (files with edges into removed symbols, and files mentioning a symbol name that appeared or disappeared), keeps an implementation edge that several files yield (a short-name collision) until none of them yields it, and rebuilds symbol cards, lifecycle evidence, use cases, documents, TODO markers, and full-text rows only for what that touches. Cargo changes replace the package tables and re-attribute crates without re-parsing sources. A changed semantic profile drops only the rust-analyzer evidence recorded under the old profile, because the syntactic index does not depend on it. `scope="git"` re-reads commit history only and publishes no generation, so freshness stays stale until sources are indexed.

Inputs are identified by content: inside Git, every input carries its Git blob id (from the index for clean files, from `git hash-object` for modified and untracked ones), so committing an already-indexed edit is not a change. Embedding vectors are content-addressed by their symbol-card hash, so a full rebuild reuses every unchanged vector even though node ids are reassigned. The semantic snapshot includes the source/Cargo digest, `Cargo.lock`, target triple, feature profile, build-environment fingerprint, and rust-analyzer version.

Opening the index is read-only once a store carries this build's schema fingerprint; migrations run once, in whichever process first opens an older store. Refresh builds in a private SQLite snapshot under the publisher lease. The shared database writer is acquired only to apply changed derived rows and publish the generation atomically; decisions, steering, quality records, and prepared contexts written during the build remain authoritative and are never copied back from the older snapshot. SQLite WAL keeps the previous generation readable during publication. Failed builds and failed publication leave that generation intact. Temporary copies require disk space proportional to the store and are removed when the operation finishes.

Refresh summaries expose `timings.copy_ms`, `build_ms`, `publish_ms`, and `total_ms`. The no-op path skips copying and publication and reports only total time. These phase timings distinguish slow analysis from publication contention. `cargo run --release --locked --example index_evaluate -- 64` exercises 2,048 functions across 64 modules; use `-- 1` for the same functions in one large file. It checks symbol counts and that documentation edits preserve source symbols and no-op refreshes publish nothing.

## Storage

Repository-local state lives under the ignored `.rust-repo-intelligence/` directory:

- `index.sqlite3` contains rebuildable source, Cargo, Git, document, graph, search, embedding, and prepared-change projections, the newest 20 snapshot-scoped architecture audits, plus the retained problem/quality/validation engine.
- `memory.sqlite3` contains research runs, evidence, findings, task history, finding review decisions, the single human-owned work store, and searchable summaries of retained legacy guidance.
- `index.lock` is the filesystem publisher lease used to reject concurrent writers.
- `sessions/*.lock` identifies live server owners of tasks and research runs. Startup recovers only abandoned owners, while records from older versions without ownership are treated as interrupted.

Consultation, context, explanations, and preparation join current work from `memory.sqlite3` read-only, including human ownership and readiness. Long intents match work by terms; mutable work state is never copied into the derived index.

Both databases use SQLite WAL mode. Index publication is transactional, while durable-memory operations use short connections and a busy timeout. Indexing never modifies repository source files.

Codex's own session history remains owned by Codex and is not copied into either Crusty database. `memory.search` reads it on demand, uses session metadata to restrict results to the exact active repository, includes side-session records represented in the thread-history projection, excludes assistant/tool/injected-context content, and returns bounded matching user prompts with provenance. This is recovery evidence, not a new canonical roadmap.

Response budgets cover the complete logical JSON payload, including freshness and metadata, at an approximate four UTF-8 bytes per token. Governance takes priority and omitted sections are counted. `serialized_bytes` and `estimated_tokens` describe that payload, excluding MCP framing and duplicate text/structured representations. Prepared contexts are persisted in full before their bounded briefing is returned; `change.get` retrieves the complete context.

Validation reports separate task completion from check outcomes through `validation_status.verdict`. Executed failures produce `failed`; unavailable checks or unresolved blocking obligations produce `incomplete`; checks not requested produce `not_run`. Cancellation and timeout are acknowledged after validation subprocesses have been terminated and reaped. Unix process groups include Cargo's descendants; other platforms terminate the direct child. Atomic index transactions finish at a safe boundary.

## Hybrid retrieval

`repo.context` and broad search combine FTS5/BM25, deterministic local symbol-card embeddings, and intent-directed typed graph expansion. Reciprocal-rank fusion combines ranks without treating lexical and cosine scores as interchangeable. Exact symbol identities always precede non-exact fused candidates, and ranking ties and graph seeds are deterministic.

The embedding unit is `symbol-card-v1`, a bounded representation of canonical identity, module, kind, visibility, crate, file, source, and typed incoming/outgoing relationships. The card hash—not merely the source node hash—keys reuse. Incremental refresh moves unchanged vectors to the new semantic snapshot and recomputes changed cards. Status and evaluation output report the model, dimensions, card version, semantic snapshot, recomputed/reused counts, and storage strategy.

The default `subword-hash-v1` model is offline and reproducible. It improves identifier-shape and vocabulary discovery but is neither a learned code embedding nor compiler proof. Dependency and impact claims require typed edges with provenance and confidence. Ambiguous short names, comments, strings, dynamic dispatch candidates, generated code, runtime registration, and external consumers remain explicit uncertainty.

GTK `.ui`, Blueprint, CSS, XML/D-Bus, desktop/service, Cargo, and common configuration artifacts participate in lexical search and invalidation. Discoverability does not prove that a runtime can instantiate or register those artifacts.

## Change preparation and validation

`change.prepare` captures a freshness-labelled impact briefing before edits. It returns a task ID, or with `wait_seconds` the settled task inline; the completed result contains the context ID, likely change surface, source slices, semantic/static provenance, governing evidence, ambiguity, validation queue, and current architecture-finding baseline. `change.get` recovers that prepared evidence by context ID, and `repo.matrix` supplies the bounded Cargo feature/profile plan referenced by its verification guidance.

`change.validate` compares a diff with that prepared context and optionally runs checks. It is also task-backed (with the same `wait_seconds`) and never refreshes first. One prepared context serves any number of validations, so a long change is validated at milestones against a single baseline. `context_id` is optional: without it, Crusty records an unprepared context that owns the diff-driven obligations and reports `architecture_delta`, `expected_affected_files`, and `unmodified_expected_callers` as unavailable with reason `no prepared context`. Its architecture delta distinguishes new, worsened, resolved, and unchanged baseline findings and considers only files touched by the diff. Inferred architecture results remain advisory; only a separately human-approved quality constraint may block. When checks are requested, locally available Rust and artifact validators report explicit pass, failure, or unavailable evidence. Runtime registration, deployment behavior, and external compatibility remain separate obligations.

Validation also returns `review_evidence`: the source revisions and published generations observed before and after the review, index staleness and its cause, and whether untracked diff inputs were skipped. Its status is `current`, `incomplete`, or `changed_during_review`. This describes evidence freshness, independently of `validation_status`, which describes executed checks. `semantic_correctness: "not_established"` and `delivery_authorized: false` remain explicit even when checks pass: live source review, revision-bound verification, and applicable runtime tests and benchmarks supply those separate obligations.

Choose one validation input: inline `git_diff`, a local UTF-8 `diff_path` (absolute or repository-relative), or `base_ref` with optional `target` (`HEAD` or `worktree`, default `worktree`). Git comparisons resolve commits locally and compare the base directly, without an implicit merge-base. `HEAD` scopes the patch to committed changes; `worktree` also includes staged and unstaged tracked changes. Omitting all inputs validates pending tracked changes against HEAD (against the index in an unborn repository) plus untracked files Git does not ignore, as new-file diffs, bounded to 500 files of at most 1 MiB; `diff_scope.untracked` lists included and skipped paths. `base_ref` comparisons exclude untracked files. Conflicting inputs, invalid refs, and unreadable patches fail explicitly. The report records `diff_scope` with resolved commits, patch bytes, and a BLAKE3 hash alongside `changed_files`; `analysis_target` remains `current_worktree`, because analysis and checks do not switch checkouts. A prepared baseline must still represent the pre-change source to provide a meaningful architecture delta; changing the diff input cannot reconstruct a missing baseline.

The minimal public quality loop exposes `problem.list/get/update`, `quality.list/get/review`, and `validation.queue/record`. Problem evidence can be completed or corrected, but activating a learned constraint requires an identified human reviewer and explicit confirmation. Constraint review history and validation outcomes are durable and inspectable. Historical constraints never create human work or expand implementation scope by themselves.

## Decisions and steering

Decisions and steerings live in `index.sqlite3` beside the derived tables but are never rebuilt; they are human records, and Crusty does not infer, merge, or expire them on its own. A decision is `accepted`, `superseded`, or `retired`, and unknown status values are rejected at write time because an unrecognised status used to make a decision permanently invisible to consultation with no diagnostic.

Memory commands commit the record, related records, review history, and search projection in one transaction. The writer is acquired before allocating IDs or reading lifecycle state, so concurrent writers cannot allocate the same sequence or close a record based on an outdated state. A database failure rolls back the command, including its search changes. This covers decisions, steering, problems, quality constraints, validation outcomes, and legacy work mutations.

Optional decision Markdown is exported after the database commit. If export fails, the response still returns the saved record ID and `committed: true`, plus `materialization.status: "failed"`, an error, and `retry_record_creation: false`. Repair the export from the saved record; creating another record would duplicate intent. This distinguishes a failed optional export from a failed database mutation; it does not promise exactly-once delivery after a transport disconnect.

Only accepted decisions govern. `repo.consult`, `repo.constraints`, `repo.context`, `repo.explain`, `repo.authority`, and `change.prepare` all read the accepted set; superseded and retired decisions stay in the ledger as history. `decision.record` may list one or more accepted decisions in `supersedes`: each becomes `superseded`, the new record keeps the forward links, and `recorded_by` is required because another human's record changes. `decision.retire` moves an accepted decision to `retired` without a replacement and requires `retired_by`. Both transitions are terminal, reject unknown or already-closed targets, append a row to the decision's `history` with the action, actor, note, and time, and rewrite the `Status:` line of any markdown the decision materialized under `docs/decisions/`. Every decision exposes `supersedes`, `superseded_by`, and `history`, and `decision.list` enumerates the whole ledger newest first when no scope is given, applies its `limit`, and accepts a `status` filter.

`repo.consult` packs one response, freshness envelope included, in authority order: decisions, steerings, approved domain models, learned quality constraints, live instruction files, governing documents, known work, lifecycle risks, and runtime contracts. Every matching item is first placed in a compact form (id, title, path) and then upgraded to full detail in that order while the budget allows, so a section is never dropped wholesale while compact forms still fit. `context_budget` reports `truncated`, per-section `omitted` counts, `compacted` counts, and a `fetch_more` hint per reduced section naming the tool that returns the rest (`decision.list`, `steering.list`, `quality.get`, `work.get`, `repo.obsolete_candidates`, or reading the listed paths); `envelope` names any of `next_steps`, `authority`, or `snapshot` dropped because the envelope alone exceeded half a very small budget. `repo.constraints` still returns the unbudgeted governing set.

Relevance is deliberately narrower than broad search. Query terms drop English stopwords and one-character words (unless nothing else remains). Topical decisions, governing documents, and runtime contracts must match enough distinct meaningful terms (one for short topics, two for 4-10 terms, three beyond, or any identifier-like term such as `audit_target`) and rank within 30% of the best BM25 hit. Known work lists only open items (closed statuses such as `completed`, `done`, `dismissed`, and `obsolete`, and stale source-comment proposals, are excluded; `proposed` stays because it is open intent an agent should not duplicate), ranked by match strength; a work item scoped to a path matches a topic that names paths only when one path contains the other. Each item is a brief (`id`, `title`, `status`, `priority`, `scope`, `summary`, `ready`) with `detail: "work.get"`. Governing documents list topical hits first (`relevance: topic_match`), then prose policy documents (`repository_policy`); CI and workflow configuration appears only when the topic concerns CI, workflows, or configuration (`ci_configuration_for_topic`), and instruction files are never repeated there. Live instruction files are always listed: root and topic-path-ancestor files are inlined when they fit (`inlined: true`), and every other file, or one that does not fit, is a stub with `path`, `scope`, `bytes`, and `content_digest` to read directly. A queried `work.list` uses the same ranking and path rules but keeps full rows and every status; an item containing the whole query phrase in its id, title, scope, or evidence still matches after the ranked ones. Steering keeps its lazy `expires_at` check, but the timestamp and the `active`/`retired` status are validated on write so a typo can no longer make a steering permanent.

Steerings mirror the decision lifecycle. `steering.record` may list active steerings in `supersedes`; with `recorded_by` it retires each target in the same transaction and records a `superseded` history row. `steering.retire` closes one active steering with `retired_by` and a required `reason`. Both are terminal, reject unknown or already-retired targets, and fill `retired_at`, `retired_by`, and `retired_reason`; every steering exposes `supersedes`, a computed `superseded_by`, and `history`. Governing reads (`repo.consult`, `repo.constraints`, `repo.context`, `change.prepare`) and the default `steering.list` select active, unexpired steerings in SQL before ranking and limiting, so retired or expired records cannot crowd out governing ones; `steering.list` accepts `status: retired` or `all` for history. Ranking: a steering whose path scope contains a path named in the topic (`path`), then one scoped below it (`path_descendant`), then symbol or concept matches (`concept`, full-text relevance over the non-path words), then global steerings with no scope (`global`), newest first within each tier and reported as `match`. Paths are compared case-sensitively after normalising `./` and trailing `/`; a bare scope entry naming an existing top-level directory counts as a path. When the topic names paths, a steering scoped only to unrelated paths does not match even if it shares words.

Steerings and decisions carry `stale_references`: path-like words in the instruction, rationale, scope, or `applies_to` (containing `/` or ending in a known file extension; URLs, absolute paths, globs, and prose such as `and/or` are skipped) that do not exist under the repository root. A bare file name is stale only when the index knows files of that extension and none has the name. No repository walk is made. `steering.record` still records the steering and returns `warnings`. Among active steerings, an older one whose newer counterpart has the same normalised title, or the same scope and a mostly shared title, is reported as `possibly_superseded_by`; that is an inference and never changes status. Consultation keeps these flags in the compact steering form and adds a next step asking the agent to have a human retire or supersede the records.

The lifecycle columns and `steering_history` table are added in place when a store opens; existing steerings stay active with empty history.

Databases written before multi-target supersession stored one bare decision ID in `supersedes`; Crusty rewrites those rows into the list form on open, and the legacy memory mirror carries the same list.

## Research, findings, and work

`research.start` performs a bounded local scan and prepares primary-first web-search queries for the attached agent. `research.list` recovers run and task IDs, while `research.get` returns the run, task, budget consumption, packet, and resulting findings. Research does not invoke arbitrary external connectors. The separate [GitHub delivery adapter](github-delivery.md) uses the installed authenticated CLI under explicit policy. The attached agent performs `web_search` and submits qualified local, primary-web, or secondary-web evidence through `research.submit`.

Every finding is categorized as technical, product, or design and begins as `proposed`. Architecture audit results remain in their report unless `audit.finding.propose` explicitly copies one into this lifecycle with local evidence, counter-evidence, and limitations. `finding.review` records an append-only human decision. When the result is `needs_evidence`, `finding.evidence.add` can append qualified evidence and reopen the proposal without discarding review history. `finding.promote` can create project work only after acceptance and explicit human confirmation.

`work.list`, `work.get`, `work.recommend`, `work.create`, and `work.update` all use `memory.sqlite3`. `work.update` covers all human-editable create-time fields. `depends_on` records prerequisite work, while `blocked_by` records work that explicitly prevents progress; both contain exact work-item IDs. Create and update operations reject unknown, duplicate, self-referential, and cyclic relationships. Supplying a relationship list replaces it, an explicit empty list clears it, and omitting it during update preserves the stored value. Reads expose unresolved dependencies and blockers plus a derived `ready` flag. A relationship resolves when the referenced work reaches `completed` (or the historical `complete` spelling). Recommendations include only human-owned, accepted or active work with no unresolved relationships; the historical `in_progress` spelling remains readable. Crusty's ledger records repository-local intent; it does not replace GitHub issues or a human product backlog.

`memory.search` is the read-only recovery boundary for human-authored Codex prompts and preserved legacy decisions, steerings, problems, and quality constraints. It does not promote, infer, summarize, or mutate work. An attached agent must present recovered intent faithfully and use explicit human-confirmed `work.create` before it enters the queue.

## Migration from 0.1

Crusty 0.3 retains the clean-break MCP API introduced by 0.2. Exact old tool names in `AGENTS.md`, Codex approval rules, or automation must be updated. See the [Codex installation and migration guide](codex-installation.md) for the mapping.

No manual SQL migration is required. On first 0.2-or-newer open:

1. Crusty creates `memory.sqlite3`.
2. Legacy work is copied into the current work store.
3. Decisions, steerings, problems, and quality constraints are preserved as legacy records and synchronized again on later opens so post-migration guidance remains visible.
4. The old index database is left in place and is not deleted by the import.

Derived evidence is intentionally migrated separately. The background refresher rebuilds a store written by another indexer version shortly after the server starts. With `CRUSTY_AUTO_REFRESH=0`, each existing project needs one explicit `index.refresh` (the default incremental scope rebuilds such a store; `scope="workspace"` forces it), polled with `task.get`, to publish indexer version 9 and the `symbol-card-v1` backfill. Projects may do this lazily. Live exact search remains available before the refresh; broad results identify the previous generation as stale.

An incompatible or deliberately reset legacy schema may lose legacy memory, so deleting state is an explicit emergency action rather than a normal upgrade step.

## Compatibility boundaries

Crusty can establish what it observed in a particular live worktree or published snapshot. It cannot establish deletion safety, external API compatibility, runtime registration, generated-code consistency, deployment state, behavior under unindexed feature profiles, or product value without additional evidence.

The index, findings, and research output are guidance and provenance. Source, compiler/runtime results, external-system state, and human decisions remain authoritative.
